# Архитектура

## 1. Принципы

1. **Слои внутри каждого сервиса** — `domain` (чистая логика, без I/O и фреймворков) → `application` (сценарии использования, оркестрация) → `infrastructure` (БД, HTTP-клиенты, краулинг) → `interface` (FastAPI-роуты, Pydantic-схемы). Формулы TF‑IDF, косинуса, метрик — чистые функции в `domain`, покрываются юнит-тестами без поднятия БД.
2. **NLP-логика вынесена в общую библиотеку** `packages/nlp_core`, а не размазана по сервисам — так лабы 2–4 подключают её, а не копипастят токенизацию/TF‑IDF заново.
3. **Границы сервисов — по зоне ответственности, а не по лабораторной работе.** Так добавление ЛР2/3/4 — это новые use-case'ы и, возможно, новые эндпоинты в существующих сервисах, а не новые копии инфраструктуры.
4. **Всё в Docker с первого дня**, один `docker compose up` поднимает систему целиком.
5. Модель данных сразу проектируется как **мультиколлекционная** (не «документы для поиска», а «документы» вообще) — так корпуса для ЛР2/ЛР3 ложатся в те же таблицы.

## 2. Сервисы

```
                        ┌───────────────┐
                        │   frontend     │  React + Vite + TS
                        │ (Nginx static) │
                        └───────┬────────┘
                                │ REST/JSON
                        ┌───────▼────────┐
                        │      api        │  FastAPI — гейтвей и оркестрация
                        │ (documents,     │  (документы, коллекции, поиск,
                        │  search, metrics)│  метрики, auth не требуется)
                        └───┬────────┬────┘
             HTTP           │        │  HTTP
                ┌───────────▼──┐  ┌──▼────────────┐
                │ nlp-service   │  │ crawler-service│
                │ (токенизация, │  │ (обход сайтов, │
                │  TF-IDF,      │  │  извлечение    │
                │  косинус,     │  │  текста)       │
                │  метрики)     │  └──────┬─────────┘
                │ импортирует   │         │
                │ packages/     │         │
                │ nlp_core      │         │
                └───────┬───────┘         │
                        │                 │
                        ▼                 ▼
                     ┌─────────────────────────┐
                     │       PostgreSQL          │
                     └─────────────────────────┘
```

- **frontend** — React SPA: страницы «Коллекции/Документы», «Краулинг», «Поиск», «Метрики качества», справка.
- **api** — единственная точка входа для фронта. Хранит бизнес-логику применения (например, «выполнить поиск» = получить вектор запроса из nlp-service → выполнить ранжирование → собрать `SearchResult`), сама не занимается NLP-математикой и не лезет в интернет напрямую.
- **nlp-service** — тонкая HTTP-обёртка над `packages/nlp_core`. Эндпоинты: `/tokenize`, `/index` (посчитать и сохранить веса терминов документа), `/vectorize-query`, `/similarity`, `/metrics/*`. Именно этот сервис — тот самый «углублённый элемент» варианта (модуль индексирования), поэтому в него вкладываем больше всего аккуратности и тестов.
- **crawler-service** — обход разрешённых источников (проверка `robots.txt`, троттлинг), извлечение и очистка текста из HTML, отправка документов в `api` (или прямая запись в БД со своей миграцией — решим на этапе 2). Управляется через job'ы: принимает seed URL, лимит документов и максимальную глубину, по ходу работы обновляет счётчики в `crawl_jobs`/`crawl_urls`, откуда их подтягивает `api` для WebSocket-прогресса (см. раздел 4 и `PROJECT_PLAN.md`, 3.1).
- **packages/nlp_core** — переиспользуемая библиотека (не сервис): нормализация текста, стоп-слова, лемматизация/POS через spaCy, TF/IDF/вес термина (формулы 1.5–1.6), нормированный TF‑IDF-вектор, косинусная мера, n-граммные профили (задел под ЛР2), сентенс-сплиттинг (задел под ЛР3), формулы метрик ROMIP.

## 4. Модель данных (PostgreSQL)

Проектируется как общая для будущих ЛР, а не только под поиск.

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `collections` | Логическая группа документов (по источнику/лабе) | id, name, language, created_at |
| `documents` | Документ (веб-страница) | id, collection_id, title, url, raw_html, clean_text, language, fetched_at, published_date |
| `terms` | Словарь лемм | id, lemma, language |
| `document_terms` | TF термина в документе | document_id, term_id, tf |
| `term_weights` | Вес термина в документе (нормированный TF‑IDF — вектор документа) | document_id, term_id, weight |
| `queries` | Пользовательский запрос | id, text, collection_id, created_at |
| `search_runs` | Один выполненный поиск | id, query_id, executed_at |
| `search_results` | Выдача по search_run | search_run_id, document_id, rank, score |
| `relevance_judgments` | Эталонная разметка (qrels) для тестовых запросов | query_id, document_id, is_relevant |
| `metric_results` | Посчитанные метрики | search_run_id, metric_name, value |
| `crawl_jobs` | Один запуск краулинга с параметрами и денормализованными счётчиками | id, collection_id, seed_urls (JSONB), max_documents, max_depth, status, documents_fetched, urls_queued, urls_failed, started_at, finished_at |
| `crawl_urls` | Фронтир обхода — состояние каждого URL в рамках job'а | id, job_id, url, depth, status (queued/fetching/success/failed/skipped), document_id (nullable), discovered_from, error |

`crawl_jobs` — то, что читает `api` для WebSocket/REST-прогресса (быстрый агрегат без пересчёта на каждый тик), `crawl_urls` — детальный лог для отладки и «живого» списка последних обработанных URL в UI.

`document_terms.tf` и `term_weights.weight` вместе — это то, что в методичке называется вектором документа (`GetDocumentVector`); `terms` + агрегат `COUNT(DISTINCT document_id)` — это источник IDF (`GetLemmInverseFrequency`).

## 5. Алгоритмы (маппинг на формулы методички)

0. **Краулинг (BFS с ограничением по глубине и количеству)**: seed URL кладутся в `crawl_urls` с `depth=0`; воркер `crawler-service` берёт из очереди URL с наименьшей глубиной, проверяет `robots.txt` и троттлинг по домену, скачивает и очищает текст, сохраняет документ в `documents` (привязан к `collection_id` job'а), извлекает исходящие ссылки и кладёт их в очередь с `depth+1`, если `depth+1 <= max_depth` и общий счётчик документов не превысил `max_documents`; после каждого URL атомарно обновляет счётчики в `crawl_jobs`. Дедупликация — по нормализованному URL в рамках job'а.
1. **Препроцессинг** (`nlp_core.tokenization`): очистка HTML → предложения → токены → нижний регистр → удаление стоп-слов → лемматизация (spaCy `en_core_web_sm`, попутно даёт POS-теги — задел под ЛР4).
2. **Индексация** (`nlp_core.weighting`):
   - `Bi = log(N / Pi)` — инверсная частота термина (1.5).
   - `Ai_j = Qi_j * Bi` — вес термина в документе (1.6), Qi_j — частота термина в документе.
   - Нормированный вектор документа `w_dk` — та же формула, что в разделе «векторная модель поиска» (TF, умноженная на IDF, делённая на евклидову норму вектора документа).
3. **Поиск**: запрос → бинарный/взвешенный вектор `Q` → косинус `r(D,Q) = (D,Q) / (||D||·||Q||)` → сортировка по убыванию → топ-K с сниппетом (первые ~300 символов) и списком совпавших слов запроса.
4. **Метрики**: Precision/Recall/F1 на топ-K, AP и MAP по набору тестовых запросов, R-Precision, 11-точечная интерполированная кривая — все реализованы как чистые функции от (ranked_list, relevant_set) в `nlp_core.metrics`, что позволяет переиспользовать их и для оценки ЛР2/ЛР3.

## 6. Технологический стек

| Компонент | Технология | Почему |
|---|---|---|
| Backend-языки | Python 3.12 | NLP-экосистема (spaCy, scikit-learn при необходимости) |
| API-фреймворк | FastAPI | Async, Pydantic-валидация, автогенерация OpenAPI для фронта |
| NLP | spaCy (`en_core_web_sm`) | Токенизация, лемматизация, стоп-слова, POS — переиспользуется в ЛР2–4 |
| Краулинг | httpx + BeautifulSoup (или Scrapy, если понадобится планировщик) | Простой контролируемый обход с уважением robots.txt |
| БД | PostgreSQL | Реляционная модель хорошо ложится на термы/документы/веса |
| Миграции | Alembic | Версионирование схемы по мере роста лаб |
| Frontend | React + Vite + TypeScript | По требованию пользователя |
| Графики метрик | Recharts (или Chart.js) | Таблицы/графики метрик в UI |
| Живой прогресс | FastAPI WebSocket + опрос `crawl_jobs` (~0.5–1 с), REST-поллинг как fallback | Progress-bar краулинга без Redis/pub-sub — таблица в БД уже источник истины |
| Контейнеризация | Docker Compose | По требованию пользователя, единая среда для всех сервисов |
| Тесты | pytest (backend), Vitest/RTL (frontend) | Юнит-тесты domain-слоя без поднятия инфраструктуры |

## 7. Задел на будущие лабы

| ЛР | Что переиспользует из этой архитектуры | Что добавляется нового |
|---|---|---|
| ЛР2 (определение языка) | `nlp_core` (токенизация), `documents`/`collections`, паттерн «тестовая коллекция + метрики» | N-граммные/частотные профили языков, новый эндпоинт в nlp-service |
| ЛР3 (реферирование) | Тот же модифицированный TF‑IDF (`term_weights`) напрямую, документы | Веса предложений (Posd/Posp), sentence extraction, интеграция с OSTIS |
| ЛР4 (машинный перевод) | Частотный список слов (ЛР1), POS-теги (spaCy уже даёт) | Таблица словаря переводов, направление перевода, построение дерева разбора |
| ЛР8 (синтез речи) | Общий frontend-каркас, документы как источник текста для озвучки | Отдельный модуль на Web Speech API/сторонний TTS |
| ЛР9 (распознавание речи) | Общий frontend-каркас, возможно — голосовой ввод поискового запроса из ЛР1 | Web Speech API для ASR, обработчик команд |

Детальную архитектуру для каждой из этих лаб имеет смысл дорабатывать перед её стартом — здесь заложена только совместимость на уровне данных и переиспользуемых модулей.
