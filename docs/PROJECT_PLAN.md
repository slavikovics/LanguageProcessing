# Проектный план — Лабораторная работа 1 (вариант 22) как платформа для ЛР 2, 3, 4, 8, 9

## 1. Формула варианта 22

| Параметр | Значение | Что это значит для реализации |
|---|---|---|
| Углублённый элемент | Модуль индексирования документов | Основной технический фокус и объём кода — на построении поискового образа документа (ПОД): нормализация текста, расчёт TF, IDF, весов терминов, вектора документа. |
| Сфера применения | Сеть Интернет | Документы поступают не вручную, а через реальный веб-краулер. Сфера отражается в модели данных (url, дата получения) и в отдельном сервисе-краулере. |
| Стратегия поиска | Векторная модель | TF‑IDF + косинусная мера между вектором документа и вектором запроса (формулы методички). |
| Язык | Английский | Токенизация, стоп-слова, лемматизация/стемминг настроены под английский текст. |

## 2. Definition of done для ЛР1

- Кроулер реально обходит заданный список источников в интернете и складывает документы в БД.
- Индексатор автоматически строит ПОД: TF, IDF (формула 1.5), вес термина в документе (формула 1.6), нормированный TF‑IDF вектор.
- Пользователь формулирует ЕЯ-запрос, система строит ПОЗ и находит релевантные документы по косинусной мере (формулы 1.7–1.8 и раздел «векторная модель поиска»).
- Выдача: активная ссылка на документ, найденные слова запроса в документе подсвечены/перечислены, дата, ранг.
- Отдельный раздел «Оценка качества»: расчёт метрик ROMIP по тестовой коллекции с эталонной разметкой, таблицы и графики.
- Веб-интерфейс: простой, с help-подсказками, доступен пользователю без подготовки.
- Всё поднимается одной командой через Docker Compose.

## 3. Тестовая коллекция и метрики (важное открытое место методички)

Файл `2004_romip_metrix.pdf`, на который ссылается методичка, в `tasks/` не найден — при возможности стоит попросить у преподавателя. Пока ориентируемся на стандартный для ROMIP/TREC-стиля набор метрик, который и предлагается реализовать:

- Precision, Recall, F-мера — на фиксированном топ-K.
- Average Precision (AP) и Mean Average Precision (MAP) по набору запросов.
- R-Precision.
- 11-точечная интерполированная кривая Precision/Recall.
- (опционально) nDCG, если вводим градуированную релевантность вместо бинарной.

Проблема: у реально скраулленных документов нет готовой разметки релевантности (qrels), а без неё Precision/Recall не посчитать. План:

1. Ограничить краулинг несколькими десятками страниц по 3–5 заранее выбранным темам (например, конкретные разделы англоязычной Wikipedia/новостного сайта с разрешённым crawling).
2. Сформировать 15–20 тестовых запросов по этим темам.
3. Вручную разметить релевантность (бинарно: relevant/not relevant) документов для каждого запроса — эта разметка и есть тестовая коллекция с эталоном, которую требует отчёт («информация о тестовой коллекции документов»).
4. Разметку хранить в БД (таблица `relevance_judgments`) и/или экспортируемом JSON — чтобы её можно было переиспользовать при доработках.

### 3.1. Управляемый краулинг с живым прогрессом

Краулинг запускается из UI, а не консольным скриптом, и параметризуется пользователем:

- **Seed URL** — список стартовых адресов (можно добавлять/удалять несколько).
- **Максимум документов** — общий лимит на job, останавливает обход по достижении.
- **Максимальная вложенность (depth)** — глубина BFS-обхода от seed-страниц (глубина 0 — сами seed, глубина 1 — страницы по ссылкам с них, и т.д.).

Отслеживание состояния — комбинированный подход:

1. **Таблица в БД — источник истины.** Job (`crawl_jobs`) хранит статус (`pending/running/completed/failed/cancelled`) и денормализованные счётчики (сколько URL в очереди, сколько успешно обработано, сколько ошибок), которые атомарно обновляет `crawler-service` по мере обработки каждого URL. Это переживает перезапуск сервиса и доступно даже без WebSocket — просто `GET /crawl-jobs/{id}`.
2. **WebSocket — push поверх той же таблицы.** `api` держит соединение `/ws/crawl-jobs/{id}`, опрашивает `crawl_jobs`/`crawl_urls` с небольшим интервалом (~0.5–1 с) и рассылает диффы подписанным клиентам — без необходимости поднимать Redis/pub-sub. Если WS обрывается, фронт просто переходит на обычный поллинг того же REST-эндпоинта — деградация без потери функциональности.
3. UI показывает progress-bar (`documents_fetched / max_documents`), счётчики очереди/ошибок и, желательно, последние N обработанных URL как живой лог.

Более real-time вариант (Postgres `LISTEN/NOTIFY` вместо опроса) возможен как последующая оптимизация, но не обязателен для первой версии — опрос таблицы раз в 0.5–1 с для progress-bar более чем достаточен.

## 6. Риски и открытые вопросы

- **Правовая/техническая сторона краулинга**: выбрать источники, разрешающие обход (проверить `robots.txt`), ограничить частоту запросов.
- **Объём ручной разметки qrels**: трудоёмко — сознательно ограничиваем коллекцию (десятки, не тысячи документов) и количество тестовых запросов.
- **`2004_romip_metrix.pdf` отсутствует** — уточнить у преподавателя точный список метрик, пока используем стандартный набор (см. раздел 3).
- Архитектура рассчитана на переиспользование, но это не значит, что ЛР2–4/8/9 нужно проектировать прямо сейчас — их детальный план имеет смысл делать перед стартом каждой из них, когда будут известны фактические требования и вариант.
